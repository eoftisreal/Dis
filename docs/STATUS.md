# Progress checkpoint — 27 October 2026
## Combined 0.4.4 preview — 28 October 2026

The local Qt desktop, single installer, embedded USB tools, permanent idle adapter cleanup, receiver watchdog, diagnostics, native touch, and two-finger gestures are combined with the GitHub APK-reference improvements. Both endpoints now report 0.4.4. The original user-supplied SuperDisplay APK matches the SHA-256 recorded in [the reference research](SUPERDISPLAY_APK_RESEARCH.md); it is not packaged with Dis.

The Android decoder retries initialization without optional scheduling hints and reports which configuration succeeded. Surface presentation uses the phone clock. ACK transport failures no longer cause subsequent sessions to select JPEG as though the hardware decoder had failed. Stylus hover/range exit, historical pressure/tilt samples, palm suppression, and bounded motion coalescing are merged without removing native touch, wheel scrolling, right-click, or touch lock. Down/up/cancel and wheel packets remain ordered and are never coalesced. Timed queue polling preserves ping and diagnostics updates while input is idle.

Local validation: 25 .NET checks; 49 Java protocol checks; 16 diagnostics checks; 26 gesture checks; bounded input-queue stress, ordering, timed poll, and shutdown checks; 12 Robolectric MotionEvent tests; Android lint with no issues; native encoding of 24 H.264 access units; Qt desktop compilation; embedded USB tool restoration/version verification. No new physical-device FPS or touch-quality result is claimed. The former mirror-probe measurements below describe an earlier receiver, not this build.

CI now builds the same Android/Qt/single-installer scripts, verifies the setup payload, independently decodes H.264, and retains the signed-driver virtual-monitor/portrait/capture and pen-injection gate on its disposable VM. CI results for this combined revision must be checked before claiming those hardware-facing tests passed.


## Single installer, background operation, and USB start

Android 0.4.3 and the paired Windows host add negotiated native touch contacts, two-finger vertical/horizontal wheel scrolling, and two-finger tap for right-click. Finger input no longer always uses a held left mouse button when the host supports native touch. Gesture slop and axis locking avoid accidental scroll/right-click transitions; per-packet wheel deltas are bounded, and Windows accumulates fractional wheel units. Pen input takes priority over fingers, and switching gestures, touch lock, cancellation, and session teardown release held contacts. Older hosts retain mouse/pen compatibility, without new gesture actions. The phone controls include an interaction guide. Native touch behavior varies by Windows app; two-finger wheel scrolling supports desktop applications that do not pan with one-finger touch. Validation passed 25 .NET checks, 49 Java protocol checks, 16 diagnostics checks, 26 gesture checks, Android lint, and the existing H.264 smoke test. A noninteractive Windows check confirmed native touch/pen device availability and Win64 input structure sizes without injecting input into other applications. Device interaction testing is still required; no real-device gesture results are claimed here.

USB packaging follow-up: `Dis.Engine.exe` now embeds the ADB executable, supporting DLLs, and notice. The app restores them automatically to a content-addressed per-user cache and checks/repairs file hashes on preparation. Legacy saved ADB paths are discarded, so deleting an old portable build cannot break the installed app's USB tool selection. ADB file-selection/download controls were removed. Published folders no longer need loose ADB executables or DLLs. Direct USB still uses ADB internally and requires Android USB debugging authorization; this is automatic dependency packaging, not a new native USB transport. Regression coverage restores missing/damaged tool files, and the build runs the real embedded tool's version check before packaging.

Android 0.4.2 replaces the floating Controls text button with a sliders icon and an adjacent touch-lock icon. Both use 48 dp touch targets, accessibility descriptions, and the existing five-second auto-hide/reveal behavior. Locking blocks display touch/pen forwarding while keeping the icons accessible; an active pointer is cancelled before locking so the remote mouse/pen is released. The lock survives transport reconnects within the activity. Android compilation, protocol/diagnostics checks, and lint passed; the new icon/lock interactions have not been tested on the phone.

Permanent connection behavior follow-up: full virtual-adapter disabling while idle is now enforced for new and existing preferences. The idle switch and Mirror screen selector were removed from both desktop interfaces; Windows display settings can manage Extend/Duplicate for the active Android display. Setup leaves the adapter disabled. Connect uses the elevated session helper every time. A receiver becomes connected only after the first frame ACK, and a watchdog cleans up failed startup (USB 30 s, network 60 s), receiver loss (3 s grace), and stalled ACKs (10 s). The helper has an independent 75 s startup/15 s renewed heartbeat lease to disable the adapter if the engine hangs. Policy/timeout regression tests and a real local TLS/capture test passed; the latter verifies that an unacknowledged stream stays unconfirmed, an ACK confirms it, and closing the receiver is detected. End-to-end elevated adapter/hung-engine cleanup still requires Windows administrator approval and has not been exercised by these checks.

Android 0.4.1 follow-up: full control packets now use one TLS socket write instead of separate writes for each header field. Regression checks cover single-write ACK/input messages and unchanged protocol bytes. Diagnostics add decoder queue-to-release, input-buffer wait, and ACK-write durations; credential-free `DisPerformance` log entries expose the same interval measurements. The Windows Display page adds capture backend and capture/encode, frame-wait, and send timings.

On the connected SM-J710F (Android 10, OMX.Exynos.avc.dec), a temporary 1280×720 primary-monitor mirror probe measured 48.6 FPS before the phone update and 51.3 FPS afterward, including intervals with the controls panel open. New phone timing samples showed roughly 8–10 ms decoder queue-to-release, 0.4–0.8 ms input-buffer wait, and 1–2 ms ACK writes. The 0.4.1 receiver was installed on that phone for the test. These short mirror measurements do not reproduce or resolve the reported 18.8 FPS after a longer extended-display session. The Virtual Display Driver remained disabled; Windows refused the attempted device toggle, and its disabled state was verified afterward. No driver was installed or removed. Local measurement records: `artifacts/phone-panel-before.json`, `artifacts/phone-ack-after.json`; `tools/StreamProbe` uses the actual capture/encoder/transport code and temporary pairing without changing preferences. Its optional `--virtual` mode requires an enabled adapter and restores a newly attached desktop on exit.

Hardware encoder follow-up: completed asynchronous output used to return before submitting the current capture. The encoder now drains output and feeds available input within the same call. A paced 1280×720 encoder-only benchmark measured 39.6 FPS before the change and 49.2–51.8 FPS afterward on the local hardware encoder. The software path measured 60 FPS on the same synthetic input. These figures exclude capture, transport, and Android; they do not establish phone FPS. The native smoke check still encoded 24 access units, and hardware benchmark timestamps remained increasing. Run `artifacts/native/Release/DisCodecBenchmark.exe` after building native targets to reproduce the six-second paced test; `--software` selects the software path, and a second argument optionally saves the H.264 stream. Local records are `artifacts/encoder-before.json` and `artifacts/encoder-after.json`.

`BUILD_ALL.cmd` now produces `artifacts/Dis-Setup.exe`, a self-contained per-user installer with the desktop, APK, ADB, codec, Qt runtime, and signed driver archive embedded. It creates a Start menu shortcut and uninstall entry, offers sign-in startup, and opens Devices for receiver installation and explicit driver setup. Uninstall retains preferences, the separately installed display driver, the Android app, and its running uninstaller file.

The Qt desktop supports tray close/reopen, tray Connect/Disconnect/Quit, quiet Windows sign-in startup, and an explicit `--quit` command. A three-second USB probe respects the phone's opt-in autostart switch, does not reconnect immediately after desktop Disconnect, and cleans up a session when its device disappears. A read-only Android provider restricted by DUMP exposes only the autostart preference to authorized ADB shell callers. This remains an ADB-based connection requiring USB debugging authorization.

Normal driver setup leaves the adapter enabled and detaches the unused desktop, removing per-connection elevation from the default flow. Existing preview preferences migrate to this mode; previously disabled adapters need Repair setup once. Full adapter disabling remains an advanced elevated option. Normal detachment does not guarantee crash cleanup, and Windows can retain the idle monitor listing.

Validation: 21 .NET checks (including USB suppression/replug policy), 44 Java protocol checks, 13 Android diagnostics checks, Android assembly and lint with no issues, and 24-picture native H.264 encoding passed. The installer payload check read every embedded archive entry and verified required runtime/APK/ADB/driver files. A Qt settings screenshot passed without startup errors. `tools/verify-desktop-lifecycle.ps1` verified close-to-tray, reopening the same instance, graceful Quit, and no orphaned engine (`artifacts/desktop-lifecycle.json`). The installer has not been installed into the user's account during these checks, and actual phone unplug/replug autostart and the revised driver lifecycle still need hardware validation.

## Historical version 0.2 changes

- Real second-display setup uses a pinned, catalog-verified VirtualDrivers/MikeTheTech x64 driver package. The original unsigned Dis driver source is retained for development.
- USB Connect opens the permission-protected Android handoff and supplies pairing automatically. A bundled APK installer button replaces separate package handling.
- Native Windows Media Foundation H.264 encoding prefers usable hardware MFTs and can select a software encoder; Android MediaCodec renders to a Surface. JPEG remains an explicit fallback.
- Windows Graphics Capture uses D3D11 to capture virtual-monitor pixels; GDI remains a fallback. The current path still copies pixels to CPU memory for conversion and encoding.
- A bounded two-frame transport window removes per-frame stop-and-wait. Native encoding stays on an MTA worker and raw-frame lifetime is protected until the native call completes.
- Windows monitor orientation controls and Android orientation controls are separate. Controlled host rotation preserves the pairing session across its restart.
- Quality presets include 720p smooth and 1080p detailed, with a target up to 60 fps and actual encoder/FPS/throughput reporting.
