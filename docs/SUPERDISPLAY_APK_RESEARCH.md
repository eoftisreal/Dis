## Findings and practical implications

| Area | Static evidence in this artifact | Implication for Dis |
| --- | --- | --- |
| Video codec | `AsyncDecoder` and `SyncDecoder` create `video/avc` MediaCodec decoders; `YUVVideoStream` gives them a SurfaceView Surface | H.264 plus direct Surface rendering is the relevant baseline; the class name does not imply uncompressed YUV transport |
| Decoder scheduling | Both decoders set `operating-rate` to 1000 on supported Android versions; the asynchronous implementation checks low-latency capability | Use explicit performance hints, with a compatibility retry. Dis requests its negotiated FPS rather than copying the hard-coded 1000 rate |
| Presentation clock | Both decoder implementations release video with the phone's `System.nanoTime()` | Keep host PTS for frame identity and use Android's clock to schedule Android presentation |
| Decoder variants | `YUVVideoStream` normally selects `AsyncDecoder`; a test setting selects `SyncDecoder` | Callback-driven decoding is an option to benchmark. Dis retains its existing two-thread decoder in this pass, reducing changes to the working baseline |
| Video flow control | Decoder output invokes a frame-done callback; `MirrorSession.onFrameDone` sends `FrameDone` associated with an encoder identifier | Acknowledge consumed decoder output. This supports the existing Dis bounded frame window; it does not reveal the Windows sender's exact queue depth |
| Cursor | `Pointer` uses a separate GLSurfaceView/OpenGL renderer, distinct position/shape updates, and a Java LZ4 decompressor for cursor images | A separately negotiated cursor channel is a valuable future improvement. LZ4 here is cursor-shape evidence, not proof of LZ4 desktop-video compression |
| Input | `Input` implements distinct touch and hover listeners, tracks pen pressure/tilt/buttons, and serializes multiple touch pointers | Add actual hover forwarding and proper pen/finger ownership now; multi-touch requires additional Dis protocol and Windows injection work |
| Session geometry | Session setup carries display/output dimensions, frame rate, quality, sampling and a software-encoder preference; portrait handling swaps dimensions | Per-device display/quality profiles and explicit encoder selection are useful next work. Existing Dis orientation and quality presets remain the current controls |
| TCP | `TCPTransportListener` binds a ServerSocketChannel on port 1445; `TCPTransport` uses the common Transport abstraction | SuperDisplay's TCP direction differs from Dis's host-listener/ADB-reverse design. Port numbers and connection direction alone do not establish latency advantages |
| USB accessory | `AOAPTransportListener`, `AOAPPipe`, and `AOAPTransport` handle Android USB accessory descriptors and file channels | AOAP is a distinct transport, not a hidden H.264 optimization. Keep ADB as Dis's default to preserve the user's working networking arrangement |
| Private framing | Transport code supports host versions 4 and 3, uses little-endian buffers and multiplexes logical streams | The APK reveals part of the private protocol; it does not recover the Windows service or justify replacing the working DIS1 protocol |
| Surface lifecycle | Surface creation starts decoding when configuration is available; destruction stops decoding. MirrorActivity handles orientation/configuration changes | Preserve explicit surface-loss recovery and separate monitor orientation from Android layout |

These findings describe code paths visible in this supplied version. No phone/GPU was exercised during the static analysis. Availability and performance of hardware decoders still depend on the actual device.

## Changes implemented in Dis

1. The Android H.264 decoder requests realtime priority and its negotiated operating rate, enables supported low-latency mode, and retries without optional hints before falling back to JPEG. The status identifies the Android codec and selected configuration. Capability queries and failed initialization now release the attempted codec.
2. Video is released using the phone's monotonic clock. Host timestamps remain output/ACK identifiers; cross-device clocks are never treated as synchronized.
3. Stylus hover, eraser and barrel-button state are forwarded. Hover exit clears Windows pen range. A pen taking over an existing finger drag first cancels that drag; fingers are ignored while a recognized pen is hovering or controlling the contact.
4. Dis retains up to eight historical pen samples per MotionEvent, including pressure/tilt, and requests unbuffered dispatch for pen contacts. **These are independent Dis enhancements:** neither a history loop nor an unbuffered-dispatch call was found in the examined reference Input class.
5. When pending input reaches eight packets, adjacent movements with the same tool/action/button state are coalesced to the latest point. Ordinary samples are retained below that threshold. Down/up/cancel, button changes, and tool transitions are never coalesced; a queue filled entirely by transitions still disconnects rather than losing a release.
6. The current ADB/TLS transport, signed second-display setup, Windows capture/encoder and orientation controls are retained. The new receiver uses the existing v2 pointer protocol; the full bundle supplies the matching hover-exit behavior on Windows.

The Android APIs above are documented in the official [MediaCodec reference](https://developer.android.com/reference/android/media/MediaCodec), [MediaFormat reference](https://developer.android.com/reference/android/media/MediaFormat), and [View reference](https://developer.android.com/reference/android/view/View#requestUnbufferedDispatch(android.view.MotionEvent)). Scheduling hints do not guarantee a particular frame rate. Windows range/contact transitions follow the official [pointer flags documentation](https://learn.microsoft.com/en-us/windows/win32/inputmsg/pointer-flags-contants).

## Next work, kept separate from completed changes

- Negotiate cursor shape/position separately, exclude the cursor from video when negotiated, and render the exact Windows cursor locally. This needs scaling, rotation, hotspot, visibility, shape-size bounds and compatibility tests on both endpoints.
- Extend the current single native touch contact and two-finger wheel/right-click gestures to independent simultaneous Windows touch contacts, plus keyboard input.
- Add remembered device profiles; the merged 0.4.4 build already provides encoder/decoder, frame timing, queue timing, and round-trip diagnostics.
- Benchmark asynchronous decoding, GPU-to-encoder texture transfer and adaptive quality on the user's actual PC/phone.
- Consider optional AOAP only after testing simultaneous Ethernet/tethering/file-transfer behavior on the target phone; it is not the default connection path in this update.

This APK cannot establish how SuperDisplay's Windows driver/encoder works internally, exact latency, complete protocol semantics, end-to-end zero-copy behavior, color accuracy or universal USB/network coexistence. Recording an audio-related permission also does not prove PC audio forwarding. No licensing or purchase logic is needed for the Dis changes.

## Reproduce on Windows

Download [JADX 1.5.6](https://github.com/skylot/jadx/releases/tag/v1.5.6) and use a local copy of the same APK. Python 3.10+ is sufficient for the inventory; JADX requires Java.

```bat
jadx.bat -d superdisplay-analysis -j 4 --show-bad-code "SuperDisplay (com.kelocube.mirrorclient) [v.1.2.22].apk"
py tools\inspect_android_apk.py "SuperDisplay (com.kelocube.mirrorclient) [v.1.2.22].apk" --jadx-output superdisplay-analysis --output apk-inventory.json
```

JADX may exit nonzero because of errors in unrelated dependency classes while still producing the focused files; inspect the diagnostics and missing-method counts. Run the inventory without `--jadx-output` for APK/DEX metadata alone. The inventory never executes the uploaded application. Consult [current verification](STATUS.md) for the tests actually completed on the delivered Dis revision.
